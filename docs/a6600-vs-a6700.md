# Sony a6600 vs a6700 firmware analysis

**Date:** 2026-11-02  
**Scope:** Static analysis of the two supplied files. No camera was connected, no target code was executed, and nothing was flashed.

### Confidence labels

- **Confirmed:** directly observed in the supplied files, including decrypted content.
- **Inferred:** reasoned from file evidence and/or cited public documentation.
- **Unknown:** not established by this analysis.
- **External context:** published specifications or community reports; these are not treated as file-confirmed findings.

## Executive summary

Both firmware payloads were successfully decrypted and their firmware tar archives were parsed completely. This was not limited to headers and strings: all **1,309,267 encrypted blocks** passed framing checksum validation, both FDAT headers passed CRC checks, and both tar archives reached their normal end markers.

The a6600 is **CXD90045, model `0x81030014`, firmware 1.10, 32-bit ARMv7**. The supplied a6700 BODYDATA image is **CXD90057, model `0x20030001`, firmware 2.00, ARM64 with four Cortex-A35 cores**. Their codec firmware, image-pipeline tables, application frameworks, memory maps and partition layouts are substantially different.

The main conclusion is that the a6700's headline features are **not exposed as a simple disabled flag in the a6600 firmware**. No readable model-to-feature table was found. HEVC/10-bit/high-frame-rate video and AI functions depend on different SoC, DSP, memory and software generations. A cross-model firmware flash would be exceptionally dangerous.

Gen4 firmware updates also contain a cryptographic signature. The symmetric decryption keys permit analysis, but **do not permit creation of a valid custom update**. Normal custom firmware flashing is therefore blocked unless a separate device-side bypass is found.

### Supplied files

| File | Size | SHA-256 | Identification |

| `Update_ILCE6600V110.exe` | 326,069,208 B (311.0 MiB) | `67a1d92be9b9d1ea3c483502918edf6423653ecadcf4b0184303b096a601d76f` | Signed Windows x86 Sony Packman self-extracting updater for a6600 v1.10 |

The a6600 executable contains an embedded DAT at offset `0xAE9D4`, length `0x12E009A8` (316,672,424 B), named `FirmwareData_ILCE6600V110.dat`. Its SHA-256 is `3ef1334de547a6884b381d5eb5cb8ad1e1f2791b56c869807604f18decff3c5b`.

**Confirmed:** the x86 architecture reported by REA/Hopper belongs only to the Windows installer, not to either camera. REA Evidence `ev_683dcd076c8dc759881a7f315aa0b37f1bddaa6b58bd49b55cf16594e89dad52` identifies the outer PE and its segments.

The installer contains Authenticode/PKCS#7 signature structures and Sony/Microsoft certificate material. Signature presence was observed; certificate-chain validity was not independently verified.

### DAT/UFU structure

Both use the same outer format:

```text
89 55 46 55 0d 0a 1a 0a       # UFU magic
BE length + "DATV" + data     # data version / body-vs-lens flag
BE length + "PROV" + data     # protocol version
BE length + "UDID" + data     # supported Sony USB product IDs
BE length + "FDAT" + data     # encrypted firmware payload
BE length + "DEND" + CRC      # container trailer
```

- `BODYDATA.DAT`: FDAT starts at `0x9C`, length `0x3D094510`; 13 USB IDs.
- a6600 embedded DAT: FDAT starts at original EXE offset `0xAEA60`, length `0x12E00910`; 11 USB IDs.
- The device ID sets differ, providing an additional model/update-target barrier.

**Confirmed:** FDAT is encrypted, not merely zlib/LZMA-compressed. Compression appears later inside the decrypted package as cramfs/squashfs and other filesystem formats.

**Confirmed with public format documentation:** Gen4 packages are cryptographically signed. Each FDAT ends with a `0x110`-byte trailer: a 16-byte CBC IV followed by `0x100` high-entropy bytes. The 256-byte value is consistent with a 2048-bit signature, and the fwtool maintainer explicitly documents a cryptographic signature. Its exact algorithm and the camera-side verification path were not established here.

## Step 2 — Decryption and unpacking

### Public tooling found

- [ma1co/fwtool.py](https://github.com/ma1co/fwtool.py) documents DAT/FDAT parsing and supports CXD90045, explicitly including ILCE-6600.
- [fwtool.py PR #52](https://github.com/ma1co/fwtool.py/pull/52) adds CXD90057 keys and reports ILCE-6700 as tested.
- [Sony-PMCA-RE](https://github.com/ma1co/Sony-PMCA-RE) documents updater/service modes and warns that CXD90045/CXD90057 firmware is cryptographically signed.
- [fwtool.py issue #21](https://github.com/ma1co/fwtool.py/issues/21) states that Gen4 repacking is blocked by the signature and missing private key.

### Algorithm validated against both files

1. Decrypt the first 512 bytes with AES-128-ECB using the shared Gen4 key1.
2. AES-256-CBC-decrypt the remaining ciphertext with the generation/key-index-specific key2; the IV is the first 16 bytes of the final `0x110` trailer.
3. Each decrypted 1024-byte block contains a little-endian checksum, payload length/end flag, up to 1020 payload bytes, and padding.
4. Validate every block checksum and the 512-byte plaintext FDAT header CRC.
5. Parse the resulting FDAT header, updater filesystem and firmware tar.

The accepted crypters were:

| Image | Crypter | Validation |
|---|---|---|
| a6600 | `CXD90045` with the original/public k0 key2 | Header CRC, all block checksums and payload sizes passed |
| a6700 BODYDATA | `CXD90057_k8` | Header CRC, all block checksums and payload sizes passed; other candidate keys failed |

| Result | a6700 | a6600 |
|---|---:|---:|
| Encrypted data excluding trailer | 1,024,017,408 B | 316,672,000 B |
| Blocks / bad checksums | 1,000,017 / **0** | 309,250 / **0** |
| Plaintext FDAT | 1,020,017,340 B | 315,435,000 B |
| Firmware tar members | 137 | 175 |
| Tar completion | Clean end marker | Clean end marker |

The plaintext FDAT begins with `UDTRFIRM`, format `0100`, mode `U`, normal LUW flag `N`, and two filesystem entries.

### Depth reached

The analysis also parsed or scanned the principal ext2/vfat images, kernels, DTB, codec files, application modules and configuration resources. The a6700 squashfs updater filesystem, NOR loader internals and Cypress `.cyacd` internals were not unpacked. Those gaps do not prevent the main camera-firmware comparison below.

### A. Processor, operating system and memory architecture

| Item | a6700 — Confirmed | a6600 — Confirmed |
|---|---|---|
| FDAT model / version | `0x20030001` / **2.00** | `0x81030014` / **1.10** |
| SoC family | `CXD90057`; `/system` also contains `CXD90057+CXD90058` | `CXD90045` crypter/platform family |
| Kernel image | ARM64 Image, `ARMd` magic | 32-bit ARM zImage |
| CPU | DTB: four `arm,cortex-a35`, ARMv8, GIC-400 | ARMv7 strings; exact core model/count not established |
| Linux | **4.9.337-scel+**, SMP PREEMPT, built 2025-05-24, gcc 6.4.0 | **3.0.27_nl-rt106+**, SMP PREEMPT RT, built 2020-07-15, gcc 4.5.1 |
| Rootfs version | `32001_06.2025052401` | `38114_02.2020071501` |
| Boot memory map | `mem=4G`, 36-bit addresses | `mem=1G@0` plus `mem=256M@0x80000000@1`: 1.25 GiB total mapped |

**Inferred:** this is a hardware-generation change, not a routine application update. Sony's BIONZ X/BIONZ XR names were not found as strings in the scanned images; those marketing names are used only as external context below.

The memory figures are boot-time maps, **not measurements of free application memory or usable burst buffer**. Runtime reservations and allocations can differ.

| Component | a6700 | a6600 |
|---|---|---|
| `/usr` | `nflasha15`, 673,741,824 B, ext2 | `nflasha15`, 215,517,184 B, ext2 |
| `/system` | `nflasha3`, 32,762,880 B, vfat | `nflasha3`, 29,458,432 B, vfat |
| Warm-boot image | `nflasha5`, 248,637,568 B, **WBI2** | `nflasha5`, 34,301,920 B, **WBI1** |

| `/cp` | `nflasha8`, 25,008,128 B, vfat | Not present in update images |
| Updater filesystem | squashfs | cramfs |
| Additional update groups | NOR loader, I2C controller firmware, CP data, AI dictionary, PMBP and LUT-related layout | Android system/data partitions, 500 MiB log partition, individual per-lens files |

**Confirmed:** `partinf.conf` uses **512-byte sectors on the a6700 but bytes on the a6600**. Offsets must not be compared without applying that unit difference.

The a6700 has an `AiDictionary` partition and `/usr/data/lut` mount; the a6600 map instead contains Android system/data partitions. The a6700 also adds `0750_nor_loader` and `1050_i2c`; its NOR configuration names TOPPERS/FMP, a CP application and PCIe firmware.

Kernel-module inventories reflect the generation change:

- **a6700:** 122 modules, including V4L2/videobuf2, PCIe endpoint, NVMe, UVC/UAC2, `r8152`, `elpmem` and `elpspacc`.
- **a6600:** 101 modules, including HDMI/CEC, NFC, motion sensors, `r8168`, `usb_darwin` and older wireless stacks.

### C. Codec and image-pipeline assets

| Asset | a6700 — Confirmed | a6600 — Confirmed |
|---|---|---|
| Codec DSP firmware | `vcd_firmware.bin`, `vcd_firmware_imola2.bin`, FPGA variant | `vcd_firmware*`, `bnl`/`bni` firmware and IPL pairs |
| PSF/image tables | `cetus`; movie tables named 8K/6K/4K/3K/2K | `musashi`; movie 4K/Bayer tables plus extensive AVC/JPEG/AAC DSP kernels |
| `av-cam.bin` | XAVC class 100/300/**480**; HEVC encoder loaders `HEVCVES.bin`, `HEVCAES.bin`, `HEVCHCFG.bin`, `HEVCYCMP.bin`, `HEVCLCMP.bin` | XAVC class 100/300; no HEVC encoder-loader names in the scanned binary |
| Encoder state modules | AVC and HEVC module lists; normal 120p/100p and 240p/200p timing code | AVC-related timing code, but no corresponding HEVC firmware-loader list |

**Important:** both packages contain shared-platform supersets. The a6700 resources mention 8K although the camera does not ship 8K recording; the a6600's common table contains 240p labels although 240p is not a shipping a6600 mode. A string or library's presence alone does not prove an exposed, sustainable camera mode.

### D. Bitrates, chroma, depth and video-mode evidence

**a6600, Confirmed:** `/bin/orb-server` contains a common record-format list spanning 6M–100M and 24/25/30/50/60/100/120/200/240p labels, including `100M 240p`, `HS120`, `HS240`, `100M 120p`, `50M 60p`, AVCHD rates and proxy rates. This is demonstrably a superset list, not a model-specific capability table.

**a6700, Confirmed:** application resources contain 38 bitrate/chroma/depth combinations from 40M through 600M, including:

- `40M 4:2:0 8bit`, `100M 4:2:0 8bit`, `150M 4:2:0 8bit`
- `50M 4:2:0 10bit`, `400M 4:2:0 10bit`
- `185M`, `222M`, `240M`, `250M`, `260M`, `280M`, `300M`, `500M`, `520M`, `600M 4:2:2 10bit`

Scenario modules expose names such as `BO_STATE_MOVIE_TYPE_HEVC_3840_100M_24P`, HEVC HD modes, XAVC AVC/HEVC selectors and bitrate/frame-rate enums. Resources name XAVC HS, XAVC S-I and DCI 4K, again as platform strings rather than a complete shipping-mode matrix.

**Negative-search boundary:** no `4:2:2`, `4:2:0`, `10bit` or `8bit` declarations were found in the scanned a6600 `/system` image, and no HEVC encoder-loader or XAVC class-480 string was found. This is evidence about those scanned binaries, not proof that no other a6600 component can name those formats.

### Shipping-mode context (External, not file-confirmed)

| Feature | a6600 | a6700 |
|---|---|---|
| Sensor/processor | 24.2 MP APS-C, BIONZ X | 26 MP BSI APS-C, BIONZ XR plus AI processing unit |
| Internal video | Up to 4K30, XAVC S/H.264, up to 100 Mb/s, 8-bit 4:2:0 | 4K60 from 6K oversampling; 4K120 with crop; H.264/H.265, up to 10-bit 4:2:2 |

### E. Feature flags and model gating

**Confirmed:** no readable model-to-feature table was found. `ILCE-6600` and `ILCE-6700` did not occur in the scanned `/usr` or `/system` images. No `MODEL_ID`, `PRODUCT_NAME`, `SUPPORTED_MODE`, `recording_time_limit` or similar table was identified.

The a6600 has `/lib/ModelCautionConfig.so` and `/lib/CautionConfig.so`, with binary mode/caution tables; the a6700 uses a different application framework (`asrid_*`/`BO_STATE_*` versus `cmnViewSetting*`). These are potential research targets, but their binary tables were not decoded and are not evidence of a specific video unlock.

**Unknown:** exact feature-flag values, sensor readout timings, thermal thresholds, recording-duration limits and any hidden engineering modes.

## Step 4 — What limits the a6600?

| Limit | Classification | Finding |
|---|---|---|
| Older CPU/OS and platform | **Hardware — Confirmed** | ARMv7/Linux 3.0 versus quad Cortex-A35 ARM64/Linux 4.9. The a6700 application and driver stack cannot be dropped into the a6600. |
| Memory capacity/address map | **Hardware — Confirmed** | 1.25 GiB mapped versus 4 GiB. The amount usable for image buffers at runtime is **Unknown**. |
| 4K60/4K120 and faster readout | **Primarily hardware — Inferred** | Different SoC/ISP/DSP generation and PSF assets strongly indicate pipeline/readout dependence. Exact sensor readout limits are **Unknown**; no software-only 4K60 switch was found. |
| HEVC encoding | **Hardware + firmware — Inferred** | HEVC encoder firmware-loader names are present in the a6700 `av-cam.bin` and absent from the a6600 counterpart. No disabled-but-complete a6600 HEVC path was found. |
| 10-bit / 4:2:2 recording | **Hardware + firmware — Inferred** | The a6700 has explicit recording resources and a newer codec stack; equivalent declarations were absent from the scanned a6600 images. A mere UI unlock is not supported by the evidence. |
| AI subject recognition/auto-framing | **Hardware + firmware — Inferred** | The a6700 has an AI dictionary partition, newer framework and (externally) a dedicated AI processor. The a6600 lacks that package/partition; this is not a confirmed flag. |
| User LUT support | **Firmware/platform — Inferred** | LUT-specific layout is visible on the a6700, not in the a6600 update. Backporting would require application/pipeline work, not copying one setting. |
| Burst depth and buffer clearing | **Memory + storage + software — Inferred** | Lower memory map and external UHS-I interface are hardware constraints. Menu responsiveness while clearing could be software-optimised, but no simple buffer flag was found. |
| Very high bitrates | **Mixed — Unknown** | Encoder, memory, thermal and card-interface headroom were not measured. UHS-I is hardware, but it is not proof that every rate above 100 Mb/s is impossible. |
| Recording time/thermal cutoff | **Unknown** | No relevant limit table or thermal configuration was decoded. |
| Language/region restrictions | **Unknown in files** | FDAT region is zero in both packages. Community service-mode reports suggest some units can be changed without a custom firmware flash, but results are version/tool dependent. |
| Custom update signature | **Firmware security — Confirmed** | Gen4 cryptographic signing blocks an ordinary modified update package. Encryption keys do not solve signing. |

There is **no confirmed evidence** that 4K60, HEVC, 10-bit, AI recognition or a larger buffer is simply switched off for market segmentation on the a6600.

## Step 5 — Possible a6600 improvements, ranked by feasibility

### 1. Language/region enablement through service-mode backup settings — **Moderate, conditional**

- **Involved:** Use the PMCA service-mode/property path rather than building a modified FDAT; make a complete backup first and change only understood properties.
- **Evidence:** Community reports include a successful a6600 language unlock, while another user on v1.10 reports `No tweaks available` and backup errors. This is not guaranteed for every region/version/tool build.
- **Risk:** Settings corruption, loss of configuration, USB-driver disruption and possible warranty consequences. It avoids the FDAT signature barrier but is not risk-free.
- **Status:** External/community evidence; not tested here.

### 2. Small, reversible configuration or in-memory tweaks — **Low**

- **Involved:** Reverse the ARMv7 checks in `orb-server`, `CautionConfig.so` and related libraries, identify a real setting, and test without writing persistent firmware.
- **Potential targets:** UI behaviour or an already implemented but hidden option. No specific safe video feature flag is currently confirmed.
- **Risk:** Crashes, invalid persistent settings and unpredictable camera behaviour. A normal permanent firmware update remains signature-blocked.

### 3. Modest AVC bitrate/record-parameter tuning — **Very low / unproven**

- **Involved:** Locate actual model-selected encoder parameters rather than the shared `orb-server` list, then validate encoder, thermal, memory and card behaviour with long recordings.
- **Risk:** Overheating, dropped frames, corrupt files, recording failures and reduced reliability. No headroom is established, and the shared 240p strings must not be mistaken for an unlock.

### 4. Buffer-clearing and menu responsiveness optimisation — **Very low**

- **Involved:** Native ARMv7 application/driver changes and extensive burst-testing. Some scheduling/UI behaviour may be software-improvable, but memory and UHS-I hardware remain fixed.
- **Risk:** Large engineering effort, data loss during interrupted writes, instability and no straightforward deployment path because of signing.

### 5. Porting a6700 HEVC, 10-bit, 4K60/120, AI or LUT features — **Not realistically feasible as a firmware tweak**

- **Involved:** New DSP/codec assets, drivers, application framework, memory layout and in several cases hardware acceleration. This is a platform backport, not a configuration edit.
- **Risk:** Near-certain failure; cross-flashing also conflicts with model IDs, USB IDs, architecture, partition units/layout and signature checks. **Do not cross-flash these images.**

### Flash/deployment risk applying to ranks 2–5

A modified FDAT would need valid Gen4 authentication. The public symmetric keys only decrypt/encrypt data; they do not produce Sony's signature. Unless a separate device-side bypass is discovered and validated, a custom update should be expected to be rejected. Attempting to bypass update/model checks can brick the camera and may void warranty/support.

## Open-gate 1080p assessment (2026-11-03)

Open gate means recording the full 3:2 sensor area instead of a 16:9 crop; a 1080-class open-gate frame would be about 1920×1280. Static analysis of the extracted a6600 v1.10 images (`av-cam.bin`, `libObj.so`, `libmpr*.so`, `libmprctrl.so`):

- Movie geometry is **enum-quantised**, not free width/height. `av-cam.bin` validates `mov_aspect_req`, `mov_size_req`, `mov_sizeh_req` and `movrec_mode_req` by comparing request bytes against backup bytes; the size enum is `PICT_SIZE_VGA/720/1080/2160`.
- All 39 movie format names use heights **270, 360, 480, 720, 1080, 2160**. No taller movie frame exists.
- `libObj.so` defines only `VALUEID_MOVIE_ASP_16_9`, `_4_3` and `_15_9`. The 4:3 and 15:9 entries are AVCHD/metadata descriptors (`pixelAspectRatio`, `Normal(4:3)/Wide(16:9)/HFR(15:9)`), not selectable recording modes.
- The only 1440×1080 path is **anamorphic 16:9** (4:3 pixel aspect, displayed as 1920×1080), not a taller frame. 960×720 is absent.
- 1920×1280 and 1920×1440 exist only in **still-image** aspect tables (`libmprctrl.so`), alongside other models' sizes. 3:2/4:3 dimensions in the capture path (1620×1080, 3240×2160, 1440×1080, 2880×2160) are width crops of 16:9-height frames used for stills/Dual-Rec JPEG.
- The AVC encoder itself is not the blocker: it opens with explicit `picture_width/height`, `canvas_size` and `valid_size`, is 4K-capable, and 1920×1280 (120×80 macroblocks) is well within its limits. No width/level/MaxFS cap was found.
- Mode gating is runtime capability-ID data (`CapIdTblMgr`, `PARAMID_CAP_INFO_*`) held in encrypted model partitions, so the exact enabled list cannot be confirmed from strings.

**Verdict:** a 1920×1280 open-gate mode is **not reachable as a configuration change** on stock a6600 firmware. It would require new aspect/size enums, movie-size tables, LiroSeq validators, UI entries, a 3:2 sensor readout mode and SPS/container metadata — i.e. a firmware modification. That remains blocked by Gen4 signature verification, and the single writable PTP property (`0xd406`) is unrelated. No camera-side test was attempted because no candidate setting exists to test.

| Item | Value |
|---|---|
| Model | Sony ILCE-6600 |
| USB ID / mode | `054c:0d0f`, MTP (PTP). Mass-storage mode had enumerated earlier as `054c:0d0d`. |
| USB serial | `<redacted>` |

| Battery | 19% on the first pass; 17% on the second pass |

Mass-storage `PMHOME` (2 MiB FAT12, mounted read-only) contained only `LICENSE/*.TXT`, `EULA.PDF`, and an empty `INFO` directory. The licence inventory lists nginx, Node.js, socket.io, libuv, OpenSSL, curl, jsoncpp, jsc/orbjs, jemalloc and Wi-Fi-supplicant components.

The first `GetModelInfo` attempt returned `DeviceBusy`; a second read-only pass with the protocol's busy retry succeeded.

### Second read-only capability pass

- Sony `GetModelInfo`: model `ILCE-6600`, product code `0032851340`, serial `<redacted>`.
- Model plist: `XMLFileType=DeviceInfoXML`, `Version=1.3.00.19200`, `Category=5`, `Feature=40832` (`0x9f80`), `Format=2114` (`0x842`), and AVIndex database version `1.0.00`. The plist version is device-metadata schema information, **not** camera firmware.
- Mounted-lens query returned type `0`, model `0xa0c530`, region `0`, version `6.00`. The lens model number was not mapped to a product name.
- Storage `0x10001` reported type `4`, filesystem `2`, access `1`, capacity/free space `0`, and description `Storage Media`; this is consistent with no usable card being present.
- The updater query again reported installed firmware **1.10** and no staged update.
- Sony command groups 1, 4 and 6 responded to supported-ID/device-information queries. Groups 5 and 7 returned `OperationNotSupported`. No registration, network, backup or power-control command was invoked.

### What the live interface permits

**Confirmed read-only access:** model/product identification, firmware version, battery state, PTP storage metadata, mounted-lens information, and PTP media/object operations if a card is present. This is useful for inventory and validation, but it does not expose the camera's firmware filesystem or video-pipeline configuration.

**Advertised write surface, not used:** PTP advertises `SetDevicePropValue` (`0x1016`). Of the five reported properties, only `0xd406` is marked writable; it is an empty string of unknown purpose. The other four are read-only. This single unknown property is **not** evidence of an open-gate, film-simulation, codec or recording-limit control, and it was not set. Sony group 4 also reported registration/network-related command IDs, but no such operation was invoked.

**Firmware modification:** the updater's read-only version query works, but no firmware-write command was sent. The Gen4 signature barrier described above still applies; PTP access does not provide a way to create a valid modified update. No safe or useful a6600 feature modification was identified through this interface.

**Safety:** no property setter, registration, backup, power-control, guard-check, mode-switch or firmware-write command was sent. PTP sessions were opened and closed; the `PMHOME` mount was read-only and was unmounted. The camera remained enumerated normally after inspection. It is still in MTP mode; switch it back to Mass Storage in the camera menu when finished.
